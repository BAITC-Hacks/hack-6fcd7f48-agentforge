# Методология и границы выводов

Роли и приоритеты — гипотезы по неполному обезличенному графу. Они помогают выбрать узлы для проверки, но не являются вероятностью преступления, доказательством виновности или атрибуцией конкретных денег. Seed-пути показывают только достижимость в наблюдаемых данных, а не хронологию переводов.

## Входная проверка

Pipeline требует непустые `nodes.parquet`, `edges.parquet` и `transactions.parquet` с нужными полями. Он проверяет целочисленные типы и диапазон int64 для идентификаторов, положительные конечные суммы, даты, глубину 0–4 и соответствие `is_seed` глубине 0. Проверяются уникальность узлов и пар рёбер, endpoints, совпадение пар и количества транзакций, а также суммы `edges` и `transactions` с допуском 0,01 KZT. Суммы, переполняющие числовой диапазон при агрегации, отклоняются с понятной ошибкой.

## Пути от seed

По графу обхода сохраняется не более одного кратчайшего пути от каждого seed к каждому достижимому узлу. Учитываются только рёбра, ведущие к строго большей глубине. При одинаковой длине выбирается лексикографически меньшая последовательность числовых `gid`. Эти правила делают пути детерминированными и не дают циклам переносить seed-метки назад или вбок.

`seed_source_count` — число разных seed с путём к узлу, исключая его собственный seed-путь; для seed это `0`. API показывает до трёх кратчайших примеров путей. Глубина задаёт ограничения обхода, а не порядок движения денег во времени.

## Форма узла сбора и роли

Перед назначением основной роли по каждому узлу вычисляется `collector_shape`: узел не является seed и не находится на границе depth=4, имеет не менее двух непосредственных входящих соседей, положительную сумму входа и отношение `out_kzt / in_kzt ≤ 0,8`. Эта форма считается независимо от первичной роли; нельзя определять её по списку уже названных consolidator. `collecting_branches` — число непосредственных входящих соседей данного узла с такой формой. Глубину этих предшественников не сравнивают: минимальная глубина узла означает кратчайшее число переходов в исходном обходе, а не хронологическую последовательность.

Условия основной роли проверяются строго в следующем порядке:

| Порядок и роль | Правило |
|---|---|
| 1. `coordinator` | Узел не seed и не boundary, получает от не менее двух непосредственных `collector_shape` предшественников и имеет `out_degree ≥ 2` |
| 2. `consolidator` | Узел соответствует `collector_shape` |
| 3. `distributor` | `out_degree ≥ 5` и `out_degree ≥ 2 × max(in_degree, 1)` |
| 4. `transit` | `pass_through` определён, обе степени положительны, `0,8 ≤ out_kzt / in_kzt ≤ 1,2` |
| 5. `terminal` | `in_degree > 0`, `out_degree = 0`, узел не seed и не boundary depth=4 |
| 6. `peripheral` | Ни одно предыдущее условие не подошло |

`coordinator` — структурная гипотеза связующего узла, не установленный организатор. Не-seed узел с `out_kzt > in_kzt` получает отдельное предупреждение: в выборке возможны ненаблюдаемые поступления или остаток до периода, поэтому полный баланс неизвестен.

Роль `terminal` описывает отсутствие наблюдаемых исходящих у внутреннего узла, в том числе с одним плательщиком. Значимость для проверки задаёт отдельный приоритет. Число плательщиков у `consolidator` может быть небольшим: критерий выделяет накопление от нескольких участников; выраженность признаков дополнительно отражает `role_score`. Полный банковский баланс из этих данных не восстанавливается.

## Сила признаков роли

`scale(x,t) = min(1, max(0, x/t))`; концентрация входа/выхода — сумма квадратов долей сумм по непосредственным соседям. `role_score` выражает силу выбранных структурных признаков и не измеряет точность роли:

- `coordinator`: `0,55 + 0,25·scale(collecting_branches,5) + 0,20·scale(in_degree + out_degree,20)`;
- `consolidator`: `0,50 + 0,30·scale(in_degree,10) + 0,20·(1 − pass_through)`;
- `distributor`: `0,55 + 0,30·scale(out_degree,40) + 0,15·(1 − out_concentration)`;
- `transit`: `0,55 + 0,30·(1 − |pass_through − 1|/0,2) + 0,15·scale(in_degree + out_degree,10)`;
- `terminal`: `0,55 + 0,25·scale(in_degree,5) + 0,20·scale(in_kzt,1 000 000)`;
- `peripheral`: `0,50 + 0,20·scale(in_degree + out_degree,4)`.

Затем score ограничивается сверху до `0,75` для boundary depth=4 и до `0,85` для seed. Итог округляется до 6 знаков. `pass_through` не определяется для seed и узла без входящего оборота; API возвращает `null`.

## Приоритет и объяснения

Weighted PageRank вычисляется собственной power iteration с damping `0,85`, максимумом 200 итераций и равномерным распределением dangling mass. Это справочная метрика, она не влияет на роль или приоритет.

Для `s=seed_source_count`, `d=in_degree`, `v=in_kzt`, `h=out_concentration`, `o=out_degree`:

```text
base = 0,35·s/(s+1) + 0,30·d/(d+3) + 0,20·v/(v+500000)
       + 0,15·h·(1−1/d), если d≥2 и o>0; иначе член концентрации = 0
priority_score = factor · base
factor = 0,5 для seed; 0,85 для depth=4 boundary; 1,0 для остальных
```

`h` — HHI исходящих сумм, то есть сумма квадратов долей каждого получателя в общем исходящем обороте. Делители `s+1`, `d+3` и `v+500000` дают мягкое насыщение; веса 35/30/20/15 и константы выбраны как эвристики, они не обучены на разметке. Итог округляется до шести знаков; равные scores сортируются по числовому `gid` по возрастанию. Название роли и PageRank в формулу не входят.

`priority_breakdown` возвращает значения, нормированные компоненты и веса формулы. `largest_out_share` — доля исходящей суммы, отправленная крупнейшему непосредственному получателю; это поле API, оно не меняет CSV-схему и не входит в формулу. Top-list и объяснение `why` используют эту долю, чтобы яснее описать концентрацию. API также предупреждает, если для не-seed узла наблюдаемый исходящий оборот превышает входящий.

## Результат на официальном наборе

Вход за июль 2026 года: 2 248 узлов, 3 119 рёбер, 4 840 транзакций, 81 seed. Расчёт выделил 91 кластер, 35 слабосвязных компонент (16 с рёбрами и 19 изолятов), 444 boundary depth=4; сумма — 365 890 012,01 KZT.

Текущие частоты: 265 consolidator, 68 transit, 118 distributor, 936 terminal, 2 coordinator, 859 peripheral. В top-20 — 18 consolidator, 1 peripheral и 1 distributor; seed нет. Два примера `coordinator`: `100000002224132100` (2 collecting-ветви, входящая степень 5, исходящая 4, `out_kzt/in_kzt=3,07`) и `100000003390036100` (2 ветви, степени 2/2, отношение 0,268). Первый пример также показывает, почему роль — гипотеза: выход выше входа требует проверки полноты баланса и данных вне выборки. Эти показатели описывают срабатывание правил; без ground truth они не доказывают точность классификации или наличие установленных организаторов.

## Ограничения и масштабирование

Переводы ниже 5 000 KZT, внешние операции и клиентские атрибуты отсутствуют. Сеть построена по исходящим переводам максимум до четырёх колен. Входящие суммы seed могут быть неполны, а у depth=4 дальнейшие переводы не выгружены; отсутствие исходящих связей на этой границе не трактуется как `terminal`.

Миллион узлов не реализован и не тестировался. Перед масштабированием потребуются замеры времени, памяти и качества: колоночная агрегация, компактный CSR/igraph, приближённый PageRank и поиск сообществ по компонентам или частям, компактное хранение достижимости seed с восстановлением путей по запросу, индексирование смежности API и ограничение отрисовываемого подграфа.
